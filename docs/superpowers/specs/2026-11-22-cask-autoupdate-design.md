# Cask self-repair in the tap — design

**Date:** 2026-11-22
**Status:** implemented — tap commit `629f973`

## Intent

`brew install --cask EricMarcantonio/duet/duet` must keep working after a
release asset is rebuilt. Yesterday it did not: `v0.3.0`'s `Duet-macOS.zip` was
re-uploaded ten hours after the cask was pinned, the digest drifted, and
Homebrew refused the download with a checksum error. Nothing noticed, because
the tap has no automation and GitHub fires no event when a release asset is
replaced.

## Goals

- A stale `sha256` in the tap is repaired without a human, within one cron
  period.
- A newly published release is picked up (version and digest together).
- No cross-repo write credentials: the workflow uses the tap's own
  `GITHUB_TOKEN`.
- A run with nothing to do makes no commit and no noise.
- A broken asset is a failed run (visible), never a silent wrong pin.

## Non-goals

- Releasing: duet's `release.yml` is untouched.
- Touching `packaging/homebrew/duet.rb` in the duet repo. That file stays a
  mirror, regenerated by `scripts/update-cask.sh` at release time; the tap
  becomes the authoritative copy for installs. A one-line README note records
  that.
- Notifying anyone on success. Failure surfaces as a failed scheduled run.
- Pull requests. The tap's `main` is unprotected and the bot pushes directly.

## Trigger

```yaml
on:
  schedule: [{ cron: "17 */6 * * *" }]   # off the hour, 4x/day
  workflow_dispatch:
```

Cron is the whole point: it is the only trigger that survives an asset
replaced out of band. Up to six hours of a broken `brew install` is accepted in
exchange for zero secrets.

## Decision procedure (pure, testable in the workflow)

1. `GET /repos/EricMarcantonio/duet/releases/latest`. Skip drafts and
   prereleases.
2. If the release has no `Duet-macOS.zip` asset yet, exit 0 with a log line —
   a release whose uploads are still running is not a failure.
3. Download the asset to a temp dir. Non-200, empty, or truncated → exit 1.
   Never pin a digest from a partial file.
4. `sha256` it.
5. Read `version` and `sha256` from `Casks/d/duet.rb`.
6. Both already equal the derived pair → exit 0, no commit.
7. Otherwise rewrite exactly those two lines (anchored, the same shape
   `scripts/update-cask.sh` uses), then re-read the file and confirm both lines
   carry the values written. A miss aborts before any commit.
8. Diff is empty after the rewrite → exit 0 (guards against a rewrite that
   silently no-ops).
9. Commit `duet <version>: pin sha256 <first12>` and push to `main`.
   Commit body names the release URL and the previous digest, so `git log` on
   the tap explains any digest change.
10. `brew style --cask Casks/d/duet.rb` as a best-effort lint on the runner;
    style offenses are logged, not fatal (the digest correctness is what
    matters, and style failures would wedge the repair).

## Guardrails

- `concurrency: { group: cask-repair, cancel-in-progress: false }` so a manual
  run can't race a cron run into two commits.
- `permissions: { contents: write }`; nothing else.
- The rewrite uses the same anchored `awk` shape as `scripts/update-cask.sh`
  so a cask edited into a different shape fails loudly instead of being
  mangled.
- The version bump and the digest bump always land in one commit, so no state
  exists where the tap names a new version with an old digest.

## Verification

Done against the real tap, not a fixture:

- `workflow_dispatch` with the digest already correct: run green, both the lint and
  commit steps skipped, notice logged as `already pinned to 0.3.0 and the current
  asset digest`, no commit.
- Stale-digest path: `Casks/d/duet.rb` pushed with an all-zero `sha256`, dispatch run,
  and the workflow produced exactly one commit (`duet 0.3.0: pin sha256 2e5c496f7190`)
  restoring the real digest. `brew install --cask EricMarcantonio/duet/duet` then
  reported "the latest version is already installed" instead of a checksum error.
